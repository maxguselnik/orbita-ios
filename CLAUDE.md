# Орбита — правила работы

Нативная iOS-игра: 3D-симулятор космических полётов в духе KSP. ТЗ — `docs/SPEC.md`, текущий статус — `docs/PROGRESS.md`, контракты модулей — `docs/CONTRACTS.md`. Эталон физики — 2D-версия в `reference/` (`index.html`, исходное ТЗ `PROMPT.md`): переносить логику, проверенную тестами.

Пользователю писать по-русски, кратко. Время называть по Москве (МСК, UTC+3).

## Окружение
- Если запущен на macOS с Xcode: собирай и тестируй сам (xcodebuild, симулятор iPhone 17 Pro), читай ошибки, чини до зелёной сборки.
- Если на Linux: физику тестируй локально (поставь Swift-тулчейн), Apple-код проверяй через GitHub Actions на macOS.
- Игру пользователь ставит напрямую через Xcode со своего Mac на iPhone 15 Pro.

## Оркестрация
- Эти правила оркестрации действуют в любой сессии и ветке, для любой задачи (этап, доработка, «сделай X»): сначала контракты, потом субагенты с моделью по сложности, затем ревью, тесты и CI.
- Ведущий агент проектирует, распределяет, интегрирует и проверяет. Реализацию отдаёт субагентам (Task tool) параллельно, где потоки независимы.
- Модели — по сложности задачи (экономия токенов без потери качества):
  - `haiku` — механика: поиск по коду (Explore), дописать случаи в `switch`, переименования, правки текстов/документов.
  - `sonnet` — обычный код по готовому контракту: вьюхи SwiftUI, эффекты рендера, звук, тесты, CI-скрипты; разбор логов CI и сверка скриншотов (Haiku хуже видит детали).
  - основная модель (сам ведущий или субагент без `model`) — контракты, архитектура, сложная физика и численные методы, Swift concurrency, падения без ясной причины, ревью F, интеграция.
  - Не уверен — `sonnet`; если субагент дважды не справился — поднять уровень.
  - Проба `haiku` на коде (с 2026-10-15): следующая простая задача по готовому контракту с тестами (не рендер, Metal, concurrency, физика) — субагенту `haiku`. После ревью F записать в `docs/PROGRESS.md`, сколько правок понадобилось; по итогу пользователь решает, оставлять ли.
- Каждый этап (и крупная доработка) — в отдельной облачной сессии: ведущий сессии этапа читает `docs/PROGRESS.md` («Следующая работа») и ведёт этап сам; управляющий чат только запускает сессии и сводит итоги.
- Перед параллельной работой фиксируются контракты между модулями: протоколы, состояние, события, ввод (`docs/CONTRACTS.md`).
- Каждому субагенту: ссылка на нужный раздел `docs/SPEC.md`, папки, которые он может трогать (без пересечений), API-контракт, критерии готовности, команды проверки.
- Потоки:
  - A Physics — `Packages/OrbitPhysics`, чистый Swift без Apple-фреймворков, свой `Vec3` на `Double`.
  - B Render — RealityKit + Metal.
  - C UI/Controls — SwiftUI: HUD, ангар, камера, карта.
  - D Audio/Haptics — AVAudioEngine, Core Haptics, CoreMotion.
  - E Build — XcodeGen, подпись, README, CI.
  - F Reviewer/QA — ревью диффа, тесты, критерии, регрессии; фичи не пишет.
- Каждый поток работает в своей ветке. Слияние в main — после ревью F, зелёных тестов и успешной сборки.
- После этапа: обновить `docs/PROGRESS.md`, дать отчёт (что сделано, что проверено, ограничения, статус сборки, что проверить на iPhone) и ждать «ок».
- Если пользователь напишет «авто»: проходить этапы подряд без остановок, пока тесты зелёные. Останавливаться, если заблокирован, провален критерий или начинается этап, где важны визуал и ощущения (2, 3, 4, 6).
- Вопросы пользователю — только при блокере, списком, с инструкцией, что нажать.
- Минимальные безопасные изменения, без лишних зависимостей, рабочее не ломать.

## Экономия контекста
- `docs/PROGRESS.md` — короткий, читать целиком. `docs/HISTORY.md` — архив, при старте не читать.
- Большие документы (`CONTRACTS.md`, `SPEC.md`, `CAREER_ECONOMY.md`, `MISSION_CATALOG.md`, `SCIENCE_TASKS.md`) — только нужный раздел: `grep -n '^#' файл`, затем `sed -n 'начало,конецp'`. В бриф субагенту — название раздела, не весь файл.
- Логи сборки и тестов — через `scripts/run.sh` (итог и ошибки), полный лог открывать только при провале и по `grep`.
- Локально по умолчанию — только тесты изменённого кода: `scripts/affected-tests.sh` выбирает наборы по диффу, его используют `check.sh`, `scripts/run.sh` и хук физики. Вручную — `swift test --filter <Suite>`, `xcodebuild test -only-testing:AppTests/<Suite>`. Полный прогон (`check.sh --full`, `FULL=1 scripts/run.sh`) — только по просьбе пользователя или при правке ядра (FlightSim, Kepler, контракты); остальное проверяет CI.
- Тесты физики (`physics-linux`) в CI идут всегда; `[build-only]` пропускает только тесты приложения. Менял `Packages/OrbitPhysics` — тесты физики должны быть зелёными до слияния.

## Стек
- Swift 6, iOS 18+, SwiftUI + RealityKit (RealityView, виртуальная камера, без AR) + Metal, где RealityKit не хватает. SceneKit не использовать — он deprecated.
- XcodeGen (`project.yml`), `.xcodeproj` не коммитить. Bundle id: `com.maxguselnik.orbita`. Подпись: Automatically manage signing (подходит бесплатный Personal Team).
- README: git pull → brew install xcodegen → xcodegen generate → открыть проект → Signing: выбрать Team → выбрать iPhone → Run. Скрипт `scripts/run.sh`: генерация, сборка, тесты.
- GitHub Actions на macOS: тесты OrbitPhysics и сборка под симулятор на каждый PR.
- Только landscape. Частота кадров 60/90/120 Гц в настройках, по умолчанию 90.
- Сохранения — JSON в Documents, локально.
- Оригинальные названия, модели, тексты и звуки. Никаких ассетов, названий и персонажей KSP.

## Структура
- `App/` — iOS-приложение (SwiftUI, точка входа, настройки).
- `App/Render/` — поток B. `App/UI/` — поток C. `App/Audio/` — поток D.
- `Packages/OrbitPhysics/` — поток A (SwiftPM, тестируется на Linux: `swift test --package-path Packages/OrbitPhysics`).
- `project.yml`, `scripts/`, `.github/workflows/`, `README.md` — поток E.
- `reference/` — эталон, не редактировать.
